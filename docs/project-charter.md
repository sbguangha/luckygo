# 立项决议：多租户营销抽奖平台（LuckyGo）

Examly（在线考试）与 NotifyHub（消息中台）均已废弃。现锁定本方向。生产级边界清单见 [production-edges.md](production-edges.md)，实现必须覆盖该文档，不允许只做 happy path Demo。

## 1. 方向（已确认）

**选定：给商家用的多租户营销抽奖 SaaS。**  
管理端配置活动，C 端打开就能转大转盘或参与到期开奖。

仓库工作名：`LuckyGo`。对外一句话：**商家自己配奖品和概率，用户当场抽或到期开奖的营销抽奖工具。**

为什么选它：页面好点、结果立刻看得见（转盘动画、中奖名单、核销）。  
必须避开的坑：不要做成「Redis 预减库存的秒杀换皮」——那种面试官听过太多。差异化靠 **奖品桶、两种开奖模型、概率与库存约束、核销、多租户**。

## 2. 这是干什么的

商家做活动：关注有礼、店庆、直播间抽奖。他们要的是：

- 配好几档奖品和中奖率、限每人抽几次
- 发一个链接，用户打开就能抽
- 实物奖能核销，不会超发 iPhone
- 活动结束能看到抽了多少、中了多少

用户侧就是一个 H5：大转盘转起来，中了显示奖品，没中显示「谢谢参与」。

## 3. 两种玩法（都要做，这是和秒杀的分界）

**即时抽（大转盘 / 九宫格）**  
用户点「抽奖」，立刻出结果。库存用 **预生成奖品桶**：活动开始前按概率和库存把 N 个名额 shuffle 进 Redis List，每次 `LPOP` 一个。桶空了只出「谢谢参与」。这样不会超卖，也不用每次 `RAND` 再去扣库存（那种会把概率打歪或超发）。

**定时开奖（更不像秒杀）**  
用户先报名/抽签号，到结束时间系统从参与者里公平洗牌抽出 N 名。用 Redis 延迟队列在结束时间触发 Worker 开奖。适合「转发抽奖」「满员开奖」。

两种一致性不同，面试要能分开讲：即时抽是库存名额原子弹出；定时开奖是报名落库 + 到期一次性洗牌，开奖任务必须幂等。

## 4. 范围切片（1–2 个月）

### 必做

- 多租户：商家注册登录，活动数据隔离。
- 管理端：创建活动、上传奖品（名称/图片/库存/概率）、开始结束时间、每人限抽次数。
- C 端活动页：大转盘或九宫格动画、抽奖按钮、中奖弹窗、滚动中奖播报、我的奖品。
- 奖品桶预生成 + 开奖前校验「各奖库存之和与桶长度一致」；概率合计必须 = 100%（含谢谢参与）。
- 每人每活动限次（Redis + 落库，防刷新刷奖）。
- 定时开奖活动：报名、到期自动开奖、结果页公示中奖名单。
- 中奖记录：虚拟奖展示兑换码；实物奖填收货信息。
- 核销：管理端扫码或输入核销码，状态变为已核销（防一奖多用）。
- 看板：参与人次、中奖件数、剩余库存。
- 接入限流（防脚本连点）；go-zero 超时/熔断按需。
- Jaeger + Prometheus；Compose 一键拉起。

### 加分（第二个月）

- 活动进行中库存/参与数近似实时刷新。
- 黑名单（某用户禁止抽奖）。
- **压测必做**：模拟瞬时点击抽奖，证明不超卖、P99 可接受，写入 `docs/loadtest.md`。数字要包含「库存 100 的一等奖，压测后中奖恰好 100」。

### 明确不做（V1）

- 微信支付、充值金币。
- 微信登录 / 复杂裂变（砍一刀、邀请助力）。
- 直播连麦、弹幕。
- Kubernetes、人脸核身。

## 5. 技术栈与部署

| 用途 | 选型 |
| --- | --- |
| 框架 | go-zero（HTTP 网关 + zRPC） |
| 主存储 | MySQL 8（活动、奖品、抽奖记录、核销） |
| 奖品桶 / 限次 / 限流 | Redis 7 |
| 定时开奖 | Redis ZSET 延迟队列 + Worker |
| 即时抽可选削峰 | 一般同步 `LPOP` 即可；压测若网关打满再对「写中奖记录」用 Kafka 异步落库 |
| 服务发现 | etcd |
| 追踪 / 指标 | Jaeger + Prometheus + Grafana |
| 管理端 | React 18 + TypeScript + Vite + Ant Design 5 |
| C 端 | 同一工程独立路由（H5 转盘，不要做成后台表格） |
| 部署 | 仅 Docker Compose |

即时抽 V1 **先同步 LPOP + 写库**，链路短、演示稳。若写库拖慢抽奖，再把「中奖记录持久化」改异步，抽奖接口仍同步返回桶里弹出的奖。不要一上来为了微服务而拆成秒杀架构。

## 6. 服务边界（4 个进程）

| 进程 | 类型 | 职责 |
| --- | --- | --- |
| `gateway` | REST | 商家后台 BFF + C 端 API；JWT；限流 |
| `identity-rpc` | zRPC | 租户、商家账号、C 端用户 |
| `lottery-rpc` | zRPC | 活动、奖品桶生成、抽奖、报名、核销、查询 |
| `worker` | 消费者 | 到期开奖；可选：中奖记录异步落库 |

```text
Admin UI / H5 转盘
        │
     gateway
        │
   ┌────┴────┐
identity-rpc  lottery-rpc ── Redis 奖品桶 LPOP
                 │
            延迟队列（到期开奖）
                 │
               worker
```

## 8. 两个月里程碑

**第 1–2 周**：登录、创建活动与奖品、生成奖品桶、C 端能转一次并出结果。  
**第 3–4 周**：限次、谢谢参与、我的奖品、核销、看板、中奖播报。  
**第 5–6 周**：定时开奖、不超卖压测、Jaeger、README（讲清为什么用奖品桶而不是 rand+扣库存）。

## 9. 怎么点着验收

两个窗口：商家后台 + 无痕当用户。

| 你点什么 | 怎样算过 |
| --- | --- |
| 后台配一等奖 1 个、二等奖 10 个、谢谢参与 | 保存时校验概率合计 100% |
| 打开 C 端活动链接 | 看到转盘、奖品列表、可点「抽奖」 |
| 点抽奖 | 转盘动画结束后弹中奖或谢谢参与 |
| 用同一账号连点超过限次 | 明确提示今日次数用尽 |
| 把一等奖库存设为 1，狂抽 | 全场只有 1 人中一等奖，后台剩余 0 |
| 中实物奖 | 能填地址；后台能点核销，不能核销第二次 |
| 建一场「2 分钟后开奖」 | 多人点报名，到点自动出名单，结果页可刷新看到 |
| 开奖后再点开奖 | 名单不变（幂等） |
| 后台看板 | 参与人次、各奖剩余库存与页面一致 |

## 10. 简历表述方向（数字待压测后填）

- 设计并实现多租户营销抽奖 SaaS：商家配置活动，C 端大转盘即时抽 + 到期公平开奖。
- 用预生成奖品桶（shuffle + LPOP）保证库存不超发，避免「随机后再扣库存」导致的概率漂移。
- 定时开奖用延迟队列一次性洗牌，开奖任务幂等；结合限流与每人限次防刷。
- 管理端覆盖核销与数据看板；Compose 一键拉起；压测证明指定奖品中奖数等于库存。
